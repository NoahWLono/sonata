# Instructions for a SONATA debugging session

You will inspect short programs. Each task states what the program should do.
Decide whether the program's observed behavior matches that intent. Some
programs behave as intended; others contain an error.

The available evidence changes between blocks. You will receive source code
with an execution log, source code with audio, or source code with audio and an
event timeline. Use only the evidence provided for the current task. The
experimenter will explain the language and sound mapping and provide practice
before timed tasks begin.

For each task:

1. Read the intended behavior and inspect the source.
2. Inspect the provided evidence. You may replay audio when it is available.
3. Say whether the behavior matches the intent. If it does not, identify the
   line or operation you suspect and explain briefly.
4. Rate your confidence from 0, no confidence, to 100, complete confidence.
5. Complete workload ratings when requested.

Tell the experimenter when you have decided. Do not edit or execute the source,
open later task folders, or consult other representations during a timed task.
You are being asked about the program; speed alone is not the objective.

Ranges exclude their upper endpoint: `1..6` visits 1 through 5. An execution
limit can stop a program that fails to terminate. The sound is a representation
of recorded execution events, and multiple events can sound alike. A timeline
entry can highlight its source line when the timeline is provided.

Use a comfortable listening volume. You may request a break, lower the volume,
or stop the session. Tell the experimenter about audio or display problems so
they can record the issue. No personal identifying information is required in
the response file.
